## 1. Executive decision

The first optimization increment should not be a renderer rewrite, a Rust rewrite, or indiscriminate removal of the game's visual charm. It should establish reliable production instrumentation, then remove work that is both invisible and already well evidenced:

1. stabilize the full-level terrain render input/model so unrelated React commits do not retrace the whole maze;
2. separate the minimap's static 529-cell terrain from its small dynamic marker layer;
3. move active-run validation/serialization off the 160 ms held-movement cadence while preserving crash-safe checkpoints;
4. requalify MOVE-01's isolated camera/actor travel wrappers against final paint/layer traces;
5. stop instantiating and fetching water, lava, and poison SVG resources on levels that do not contain them;
6. regenerate and prove a current retirement-candidate ledger for Plan 12, then quality-test active audio and oversized-image reductions family by family;
7. add explicit static-host caching for hashed code and versioned media without introducing a service worker or weakening Tauri offline behavior.

The current baselines in the brief are substantially correct. A fresh release-mode Vite build reproduced the existing local ignored `dist` byte for byte: one 384,157 B JavaScript chunk, one 136,287 B CSS chunk, and 139 runtime media assets occupying 89,330,098 B. The current locally staged Windows portable executable is 97,871,360 B and the NSIS installer is 91,784,124 B. Media is the dominant lever: runtime media is 91.27% of the portable executable, whereas raw JavaScript plus CSS is 0.58% of `dist`.

The browser inspection also confirmed two important scope boundaries. The title does **not** fetch the whole art catalogue: an isolated title loaded eight unique images, 1,477,675 encoded bytes in total, plus the one script and stylesheet. Conversely, the first ordinary maze fetched all three hazard textures even though that level has no water, lava, or poison, because their SVG patterns are emitted unconditionally.

Some timing work remains a Phase 0 release gate rather than a trustworthy baseline. Concurrent local planning builds saturated the eight-logical-processor/8 GB reference host. A desktop start smoke run was useful for process topology, but the larger cold/warm cohort produced impossible outliers and orphaned processes; those results are rejected, not averaged. Headless Edge timing traces run under the same contention are labelled contaminated. No numeric Lighthouse, frame-time, INP, heap-retention, or Tauri-start claim in this plan is promoted from contaminated evidence. This is intentional evidence hygiene, not a waived requirement.

**Historical baseline limitation:** the original research did not establish a complete measured timing baseline. Later 07A accepted infrastructure and deterministic evidence without promoting contaminated timing. Clean affected before/after cohorts still gate numerical improvement claims; missing unrelated hardware cells do not block safe deterministic work. Final performance support claims require the qualified applicable matrix, with pending cells disclosed.

## 2. Goals, non-goals, and evidence vocabulary

### 2.1 Goals

- Make title load, level entry, movement, effects, Book use, transitions, and Tauri launch measurably faster and more stable on recorded reference and low-end profiles.
- Eliminate work players cannot perceive while preserving semantic feedback, art sharpness, lighting readability, audio quality, accessibility, reduced motion, save integrity, and offline desktop play.
- Give the UI, art, lighting, VFX, animation, controls, gameplay, audio, and release owners budgets that can be enforced before their plans land.
- Make every performance comparison reproducible from an exact commit, lockfiles, release build, engine version, viewport, throttle profile, run count, and raw artifact.
- Reduce runtime/package media by at least 25% if blind listening and visual qualification allow it; otherwise publish the measured quality frontier and adopt the largest defensible reduction with an explicit exception.

### 2.2 Non-goals

- No implementation, manifest edit, asset deletion, re-encoding, dependency addition, Cargo profile change, or release-document correction belongs in this planning change.
- Do not redesign gameplay rules, art direction, lighting, VFX choreography, sound identity, layouts, or accessibility behavior under the guise of performance.
- Do not replace the local/offline Tauri resource model with a CDN, network-first cache, or remote music.
- Do not add a service worker merely to improve repeat-load scores. Static immutable caching is sufficient for this plan; a PWA is a separate product and update-semantics decision.
- Do not compare development Strict Mode, profiling React, Lighthouse, normal release tracing, headless Edge, headed Edge, or WebView2 values as though they came from one population.

### 3.4 Measurement protocol

1. Build from the recorded clean commit into a new temporary output directory. Hash the output and compare it with any existing local or staged artifact before reuse.
2. Close all test-owned Edge/WebView/Tauri processes. Leave unrelated user processes untouched. Sample total CPU once per second for 60 seconds; start only when median is below 20%, maximum below 50%, AC power is stable, and no build/indexer/antivirus scan is active. If this gate fails, postpone rather than normalize the noise away.
3. Use serial runs only. Navigation: at least five cold and five warm runs per primary profile; user flows: at least three runs per scenario/profile; ten-minute memory stress: at least three complete cycles. Report median, p95 where the sample is large enough, worst, raw run values, and failures. For three or five values, label the upper-order statistic “worst,” not statistically robust p95.
4. “Cold web” means a new browser context, cleared HTTP cache, empty origin storage, no service worker, and a fresh navigation. “Warm web” means the same engine/profile with HTTP cache warm and a reload; origin state is otherwise documented. “Cold Tauri” means no app process, no test WebView descendants, and a reboot-or-validated-cold OS cache cohort. “Warm Tauri” means a second launch with the same clean user-data folder after a controlled close.
5. Start timing from navigation/start-process. End title TTI when the title action is visible, enabled, and a synthetic trusted-equivalent test action receives its handler by the next paint. End “first playable” when the maze is visible, the input policy is unlocked, the first directional action can update state, required visible art is decoded, and no entry long task remains queued.
6. Collect a normal Performance trace first. Paint flashing, layer borders, screenshots, React profiling builds, heap snapshots, allocation sampling, and Lighthouse each add overhead and run in their own cohorts. Compare the shape of work across tools, not their absolute timings.
7. Force GC only at documented memory checkpoints when DevTools/launch flags permit it. Measure JS heap, DOM nodes/listeners, renderer private working set, image/GPU estimates, WebView process tree, and OS working set separately. DevTools itself can retain objects; close it for the release memory cohort.

## 8. Subsystem findings and intended architecture

### 8.1 React rendering

`App` owns broad screen, game, modal, presentation, audio, and input state. Many derivations run before the active-screen branch and only `MazeTerrain` and `MiniMap` are materially memoized. The plan is to isolate stable render models and state publication boundaries, not to scatter `useMemo` everywhere.

- Build a `TerrainRenderModel` once per immutable level/material/light input. Pass primitives or one stable model to an extracted `MazeTerrain`; expose a development counter and User Timing span around model construction and render.
- Split `MiniMap` into a static terrain grid keyed by level/reveal topology and a small dynamic layer for player, exit, and guided markers. If reveal changes, patch only changed cells or a compact bitmap/class map. Preserve the hidden visual map plus textual location/goal equivalent.
- Reuse the exploration `Set` when no cell is newly revealed. Stabilize active-object view models by level/game revision rather than allocating through every parent render.
- Put React `<Profiler>` around App shell, Maze scene, terrain, minimap, HUD, Book, and each presentation in a dedicated profiling build. Record `actualDuration`, `baseDuration`, commit time, and interactions; never compare its overhead with ordinary release traces.
- Do not make `App` one global external store as a first step. Extract components along ownership seams proposed by the UI/VFX plans, then measure whether context selectors or `useSyncExternalStore` are necessary.

### 8.2 SVG, DOM, camera, and animation

- Keep connected SVG terrain paths; they already avoid one DOM node per world tile. Cache geometry independent of camera motion and conditionally emit only material definitions present in the level.
- Consume the accepted MOVE-01/scene wrappers: outer camera travel; actor/world position; presentation travel/recoil; inner sprite pose; sibling aura/contact effects. Optimize within those boundaries and leave only one owner for each `transform`.
- Remove permanent `will-change` after traces confirm promotion timing. Apply it immediately before bounded travel and clear it on transition end/cancel. Inspect layer count and GPU memory; transform/opacity are candidates, not a guarantee of cheap pixels.
- Separate static SVG material/mask content from the smallest animated overlay. Tighten filter regions, blur radii, blend surfaces, and mask extents only after paint/raster evidence. A full-board blurred layer should have a static no-blur/lite fallback.
- Keep DOM for semantic controls and a textual minimap alternative. Canvas/WebGL is an escalation only if the cached SVG/DOM design still fails the low-end frame budget in three clean cohorts.

### 8.3 Persistence and save integrity

The active-run write should be decoupled from every movement render without weakening recovery:

- construct and validate invariant level/session metadata at entry, not for every step;
- serialize only after a state revision is marked dirty;
- checkpoint ordinary movement at a measured debounce interval, after important transitions (pickup, rescue, combat, door, completion), and on `visibilitychange`/`pagehide`/Tauri close where the platform permits;
- keep synchronous final flush small and bounded; do not move correctness validation exclusively to writes—strict validation remains mandatory on reads/migrations;
- skip `removeItem` when no active-run key exists and do not persist generated runs unless the gameplay plan explicitly adopts a versioned generated-run contract;
- preserve the last known-good record on quota, unavailable-storage, malformed-write, or migration failure and expose nonfatal diagnostics.

Tests must close/crash at each boundary in any approved batching window, load every currently supported schema (the September 5 contract includes active-run v3/progress v5 and their historical readers), simulate quota/unavailable storage, and compare recovery against the engine transition log. Cover pending completion, Stay on the exit tile, exactly-once Next receipts and stationary open-door origin. No scheduling change may turn an unbanked pending choice into durable rewards or weaken migration/read validation.

### 8.4 Assets, images, and loading

- Add a generated asset manifest with path, owner, route/level/region, reachability, encoded bytes, dimensions/duration, measured maximum rendered CSS size/DPR, hash, preload tier, and offline requirement. Report-only first, then fail on new unowned bytes or unexplained candidate reachability.
- Regenerate the retirement-candidate ledger from the final manifests and give Plan 12 exact proof/rollback records; Plan 07B does not archive or delete those files.
- Record maximum rendered CSS size and DPR for every real consumer before resizing any active family. Prioritize measured over-delivery rather than historical source-dimension buckets. Verify region seams, alpha fringes, masks, repeating patterns, Book/modal reuse, TV/iPad, DPR2, and 200% zoom.
- Resolve the current level—including concrete generated cast and every visual region—before building its dependency closure. Decode only first-visible art before the “playable” mark; queue bounded current/nearby-region dependencies with URL deduplication and cancel obsolete entry/restart work. Use `HTMLImageElement.decode()` as readiness, not as evidence that memory has been reclaimed.
- Select one runtime encoding per use wherever possible. Temporary old files remain under the accepted rollback/Plan-12 retirement contract and count honestly toward current package bytes; they are not permanent fallback loading. If two sizes are justified for title versus modal reuse, document both consumer need and package crossover.

### 8.5 Audio

The historical 34.5-minute soundtrack has been replaced by the delivered contextual 42-track OST and must be freshly inventoried. Continue to use streaming `<audio>`, not full-file Web Audio decode. Preserve gesture-gated start, mute semantics, failure isolation, one current music player, and at most one bounded likely-next track prepared for the pending context transition.

- Instrument request start/abort/range bytes, media ready state, time-to-audible, loop boundary, media-process memory, and dispose completion.
- Fix same-gesture title-to-maze track competition only if a trace confirms a title request begins and is abandoned.
- Verify that every title/story/maze/victory/garden/Adventure Book transition fades without silence while never preloading an entire contextual playlist. Previous/next/shuffle/loop actions may change selection state, but speculative loading remains current + one likely-next and stale work is cancelled.
- Transcode from verified owner-held source exports if they are supplied, using a pinned encoder/settings matrix. No WAV, FLAC, AIFF, or other lossless audio master is present in the audited repository. If owner-held sources are unavailable, label every trial as lossy-to-lossy re-encoding and apply a stricter listening/quality gate. Blind or level-matched ABX/listening trials cover all tracks, headphones/laptop speakers, quiet intros, bass-heavy tracks, loops, and fades.
- Test a single broadly supported result against the documented release matrix, including Edge/Chrome, iPad Safari, and the installed WebView2. `canPlayType` is only a capability hint; actual decode and offline package tests are required.
- Never establish MP3 plus its replacement as a permanent dual-format fallback. Count temporary rollback copies until Plan 12's authorized retirement; restore prior mapping/hashes if compatibility or quality fails.
- Keep short synthesized SFX in `src/sound.ts`: lazy AudioContext creation, cleanup, and the 24-voice cap are sound foundations and currently low-risk.

The operational feature is PT20/PT23, not merely smaller MP3 files. Resolve one
typed context from accepted UI truth: title/Home, Story, maze, pending completion,
Book and the reserved Garden context. Help/Hint/Sound/confirmation overlays
inherit their underlying activity; ordinary combat does not select victory.
Create the controller behind the current port with an injected clock, selection
seed and media adapter. Preserve its conformance fake so UI/Controls do not
migrate again.

- Separate requested context/selection from the currently audible lane. A late
  old callback cannot publish a track, advance history, resume or change mute in
  a newer generation. UI reflects loading/failure truth without claiming audio
  started merely because a URL was selected.
- Use per-pool session shuffle bags with no immediate repeat where possible.
  Same-context render consumes no draw. Previous uses actual audible listening
  history in that context, not filename order; failed/cancelled candidates make
  no history entry. Next/Shuffle and natural succession use the same selector.
  Loop stays unavailable unless the Human separately approves its scope and
  persistence; context changes override any later loop choice.
- At most two long-form lanes exist: audible current and one selected successor.
  Never fade/dispose current before successor readiness. Rapid manual commands
  replace only stale standby work; exhausted target candidates retain the last
  safe music with a bounded diagnostic. Retry each failed candidate at most once
  per transition generation, then await a new context or deliberate action.
- Context churn during a crossfade must remain click-free with no zero-gain
  interval and no third lane. Choose and test a documented retarget policy for
  the two existing lanes; cancelling a fade cannot leave both silent or reset
  gain unexpectedly. Natural track ends, leading/trailing silence and MP3 gaps
  need actual listening proof as well as fake-media tests.
- Mute remains user-owned across all transitions. Hidden/suspended state pauses
  both lanes and time-based envelopes; resume targets only the current context
  and never races a stale `play()` promise. Autoplay rejection retries only on a
  fresh explicit permitted gesture, never each poll/frame. Total media/device
  failure remains nonfatal with honest silence status.
- Set a measured loudness/peak and BGM/SFX balance policy. Do not remaster or
  transcode a Human track merely to normalize the file inventory. Preserve
  source/provenance and require the documented quality approval for any changed
  audio representation; essential cues remain distinct without drowning music.

### 8.6 Delivery, caching, and code splitting

- Keep `index.html` and deployment metadata short-lived/revalidated. Give content-hashed JS/CSS `public, max-age=31536000, immutable`. Give explicitly versioned media a long immutable policy only when filenames change with content; otherwise add content hashes or a bounded cache lifetime first.
- Preserve local, static-host/Tauri-compatible root-relative `/assets/...` URLs, or explicitly validate any future Vite `base`/subpath migration. Keep Tauri `frontendDist`; do not introduce runtime server APIs.
- Add route/feature dynamic imports for truly optional code—Surprise generator/solver, tester-only controls, Book data/view, and heavy one-shot presentation directors—after a bundle analysis demonstrates parse/eval savings. Do not split the small React runtime blindly or use fragile manual vendor chunks.
- Make `index.html` preload only a proven title LCP resource. Over-preloading optional images competes with the title and maze entry.
- The LCP resource is now proven to be the title background and not initially discoverable. Trial an initial-document preload plus responsive/right-sized title derivatives in separate commits so discovery and byte savings can be attributed independently.
- Add a metafile/bundle report and compressed-size budget. Source maps belong in protected CI artifacts if enabled; do not ship public maps by accident.

### 8.7 Tauri and WebView2

`src-tauri/src/lib.rs` and `main.rs` expose no source-level hot path, so Rust tuning is deliberately last until ETW proves otherwise. The 0.19.0 config builds `../dist` into one centered, resizable 1280×720 window with a 960×540 minimum, targets NSIS, allows only the `main-window` capability with `core:default`, and uses a self/local-data/media CSP with no remote game origin. Tauri owns launch/window/update/offline qualification; runtime cost allocation among host, WebView, renderer, GPU, media, and frontend remains unmeasured.

- Add a release-only startup mark from process start, document creation, React root, title interactive, maze playable, and first input response. Correlate CDP marks with ETW/WPR process, disk, CPU, and GPU events.
- Record the actual WebView2 child version and full process tree for every run. Separate host, browser, renderer, GPU, utility, and media working sets.
- Use a fresh, local, fast user-data directory for cold-profile qualification and a stable production-like folder for warm/reopen/save tests. Do not place it on a network path.
- Test show-on-ready/background-window behavior only if a trace shows a visible blank interval. A hidden window can improve perceived startup while worsening actual TTI; gate both and retain a watchdog.
- Keep the current narrow capability (`core:default`) and CSP. Test offline with networking disabled, a preinstalled supported WebView2 runtime, packaged assets, save/resume, resize, hide/show, and reopen. “Offline app content” does not mean the installer itself provisions WebView2 offline.
- Consider stripping/LTO/panic settings only after a binary-section report shows a material remaining opportunity. Land one Cargo/profile change at a time and compare identical release modes.

Current `docs/PERFORMANCE_BUDGETS.md` and reviewed feature allocations are operational authority; section 11 retains targets that must be reconciled against them. ### 12.5 Limited sprite animation

- Outer world position, presentation travel, inner sprite frame/pose, weapon socket, and aura/contact each have one transform owner.
- Frame selection uses absolute rAF time and an isolated renderer; no per-frame App render and no timer catch-up burst.
- At most two Tier-1 decode jobs and one background job run concurrently. The strong decoded cache is at most 16 **field-equivalent units**: one 256² RGBA frame is one 256 KiB unit and one 512² frame is four. This caps CPU RGBA at 4 MiB and should be budgeted as about 8 MiB with a comparable GPU/compositor copy; visible/current frames are pinned and everything else is evictable.

### 12.7 Audio

## 15. Research basis and implications

Research was checked on 2026-09-02 against primary/official documentation. Source claims and project inferences are separated below.

### 15.1 Web Vitals and laboratory evidence

- Google's current “good” thresholds are LCP ≤2.5 s, INP ≤200 ms, and CLS ≤0.1 at the 75th percentile, evaluated separately for mobile and desktop. Lab tools cannot reproduce field users/devices/network distributions, so this plan retains both field and lab gates ([Core Web Vitals thresholds](https://web.dev/articles/defining-core-web-vitals-thresholds), [lab and field differences](https://web.dev/articles/lab-and-field-data-differences)).
- Lighthouse user flows cover interactions beyond a navigation, while navigation TBT remains a diagnostic proxy rather than INP. This is why gameplay/Event Timing and field INP are distinct rows ([Lighthouse user flows](https://web.dev/articles/lighthouse-user-flows)).
- Lighthouse results vary with host load, hardware, network, and page nondeterminism; Google's guidance supports stable environments and repeated runs. Its throttling documentation distinguishes simulated and observed modes. This plan rejects the saturated host cohort rather than presenting a favourable sample ([Lighthouse variability](https://github.com/GoogleChrome/lighthouse/blob/main/docs/variability.md), [Lighthouse throttling](https://github.com/GoogleChrome/lighthouse/blob/main/docs/throttling.md)).
- A task over 50 ms is a long task; breaking or removing long main-thread work protects input responsiveness. The project implication is a hard no-long-task gameplay gate and explicit persistence/generation timing ([Optimize long tasks](https://web.dev/articles/optimize-long-tasks)).

### 15.2 Chrome/Edge rendering and memory

- The Performance panel exposes tasks, interactions, frames, style/layout, paint, raster, network, and memory; the Rendering panel exposes paint flashing, layer borders, frame stats, and GPU-related diagnostics. Instrumentation such as paint flashing adds overhead, so it runs separately ([Chrome Performance panel](https://developer.chrome.com/docs/devtools/performance), [Chrome Rendering performance features](https://developer.chrome.com/docs/devtools/rendering/performance)).
- Edge's heap snapshots, comparison views, allocation sampling, detached-elements and retainers answer JS ownership questions; JS heap is only one part of browser/WebView memory and DevTools can itself retain objects. The project therefore gates heap slope, DOM/listeners, renderer private bytes, image/GPU concerns, and OS process memory separately ([Microsoft Edge memory tools](https://learn.microsoft.com/en-us/microsoft-edge/devtools/memory-problems/)).
- WebView2 uses a Chromium multi-process architecture. Microsoft recommends fast local user-data storage and profiling the actual host/browser/renderer/GPU behavior. The project inference is that six WebView descendants in one smoke run are normal topology evidence, not six leaks ([WebView2 performance guidance](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/performance)).

### 15.3 React 19

- React's `<Profiler>` reports `actualDuration` and `baseDuration`, but profiling adds cost and production profiling requires an explicit profiling build. React 19.2 Performance tracks add scheduler/component/effect context. Hence the separate profiling lane and ordinary release lane ([React Profiler](https://react.dev/reference/react/Profiler), [React Performance tracks](https://react.dev/reference/dev-tools/react-performance-tracks)).
- `useMemo` dependencies are compared with `Object.is`; a fresh object dependency/prop is different on every render. This directly supports the source diagnosis around `fullLevelWindow`, while runtime benefit still needs measurement ([React `useMemo`](https://react.dev/reference/react/useMemo)).

### 15.4 Vite 8 and static assets

- Vite 8 uses Rolldown/Oxc and Lightning CSS, with current Node requirements and modern browser defaults described by the release. Project versions satisfy the recorded build; future baselines must pin them because bundle output can change across Vite releases ([Vite 8 announcement](https://vite.dev/blog/announcing-vite8)).
- Vite's default build can split CSS and module-preload dynamic imports; `public/` files are copied to the output unchanged and retain their names. Dynamic imports and lazy globs are valid feature boundaries; manual chunks require care around side effects. This explains why the historical source scan found 17 packaged candidate files without literal consumers and why route-level imports, not public-asset tricks, are the right code split; final reachability must still be regenerated ([Vite build options](https://vite.dev/config/build-options), [static asset handling](https://vite.dev/guide/assets), [production build guide](https://vite.dev/guide/build)).
- Project inference: immutable caching is safe for hashed code and genuinely content-versioned media, but never for `index.html`; cache correctness depends on filename/content discipline, not Vite alone.

### 15.5 Tauri 2 and WebView2

- Tauri uses the operating system webview rather than bundling one universal browser engine; Windows uses WebView2 and the installed version can vary. The current release must record its actual spawned version and cannot infer Windows results for WebKitGTK/WKWebView ([Tauri architecture](https://v2.tauri.app/concept/architecture/), [Tauri webview versions](https://v2.tauri.app/reference/webview-versions/)).
- Windows installer choices and WebView2 installation modes are deployment concerns. The current application bundles local game assets but depends on an installed/supplied runtime; “offline playable” and “offline WebView bootstrap on a clean OS” are separate claims ([Tauri Windows installer documentation](https://v2.tauri.app/distribute/windows-installer/)).
- Project inference: because `dist` is 91.87% of the portable and Rust has no commands/plugins, frontend/media changes precede Cargo micro-tuning. Only ETW/binary-section evidence can overturn that order.

### 15.6 Animation, images, and audio

- Browsers can often composite transform/opacity without layout/paint, while geometry properties commonly require more pipeline work. `will-change` and extra layers consume memory, and expensive pixels such as large blur surfaces remain expensive even if animated on a compositor. Thus transform migration is trace-gated, not a blanket “GPU = free” claim ([web.dev animation guide](https://web.dev/articles/animations-guide), [Chrome animated blur analysis](https://developer.chrome.com/blog/animated-blur)).
- Image transfer bytes and decoded memory are different. Right-sizing, modern encodings, dimensions, lazy loading, and decode timing should be chosen by use; `HTMLImageElement.decode()` resolves readiness but does not promise cache eviction ([web.dev image performance](https://web.dev/learn/performance/image-performance), [MDN `decode()`](https://developer.mozilla.org/en-US/docs/Web/API/HTMLImageElement/decode)).
- Audio codec support and quality vary by engine/container. Long music should remain streamed media; full `decodeAudioData` can expand it to roughly 10.1 MiB/min mono or 20.2 MiB/min stereo for 44.1 kHz 32-bit-float channel data, before implementation overhead. Test actual playback, loops, ranges, and media-process behavior, not extension support alone ([MDN audio codec guide](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats/Audio_codecs), [Chrome Media panel](https://developer.chrome.com/docs/devtools/media-panel)).

## 16. Risks, dependencies, and decision log

| Risk / dependency | Mitigation / decision owner |
|---|---|
| Shared development host makes timing flaky. | Performance owner schedules dedicated serial hardware; reject busy-host cohorts. Deterministic byte/correctness gates can still run in ordinary CI. |
| Concurrent plans edit the same `App.tsx`/`styles.css`/terrain layers. | UI owns component/layout seams; lighting owns topology/light data; VFX owns transient layers; animation owns inner poses; performance owns trace/budget/quality-tier policy. Rebase phases, do not duplicate components/styles. |
| Persistence batching loses recent movement. | Save/gameplay owners approve checkpoint contract; exhaustive crash/close matrix and last-known-good recovery block release. |
| Transform migration changes hit testing or effect composition. | Nested one-owner wrappers, final-coordinate parity tests, feature-flag rollback, pointer/focus tests. |
| Media reduction damages charm/quality. | Preserved image sources and any owner-supplied audio exports, real-size visual matrix, blind listening, explicit second-generation-loss labelling when only MP3 exists, one family per commit, explicit quality exception. |
| Codec works in Edge but not a supported mobile browser/WebView. | Publish supported-engine matrix; actual decode/loop/offline tests; ship one qualified representation only. |
| Lazy chunk fails offline or on static direct navigation. | Every chunk lives under local `dist`; static preview/direct URL and network-disabled Tauri tests; recoverable UI on failure. |
| Long immutable cache serves stale media. | Hash/version filenames with content; revalidate HTML; automated cache-header/content-hash assertion. |
| Adaptive quality silently reduces semantics. | Stable full/lite/static policy, never single-frame auto-downgrade; all tiers retain exact gameplay information and accessibility. |
| Desktop startup target is missed after frontend work. | Correlate process/frontend marks; only then trial show-on-ready or Cargo profiles; document measured quality/OS limits rather than hiding TTI. |
