## 1. Native Exit: actual defect and smallest seam

`src/ui/screens/FrontDoorScreen.tsx:17` calls browser `window.close()` and schedules
a browser-only notice after 180 ms. This matches the native release observation:
web content closes but a Tauri window can remain. `src-tauri/src/lib.rs` is only
the default builder; there is no custom close handler, tray lifecycle or shutdown
coordinator to untangle. The app has one configured window, `main`.

Two integration gaps must be fixed together:

- `src-tauri/capabilities/main-window.json` grants only `core:default`. The locally
  generated `desktop-schema.json` shows that its nested `core:window:default`
  does **not** include `core:window:allow-close`.
- `package.json` has the CLI, not `@tauri-apps/api`; `tauri.conf.json` does not
  enable the public global API. Merely pasting an API call into the component
  is not an implementation.

Prefer a tiny platform-close adapter, invoked only by the existing Exit button.
One no-new-package route is explicit `app.withGlobalTauri: true`, a narrow typed
adapter for `window.__TAURI__.window.getCurrentWindow().close()`, and the one
additional `core:window:allow-close` permission on the existing `main` capability.
The public global is documented, not an internal IPC hook. Keep all other
permissions/CSP/window geometry unchanged; account for actual native/bundle byte
changes. The alternative is an explicitly reviewed official API dependency; do
not silently add a process plugin or a broad native abstraction for one button.
See Tauri's [global API configuration](https://v2.tauri.app/reference/config/#withglobaltauri),
[API entry](https://v2.tauri.app/reference/javascript/api/) and
[documented close API/permission example](https://v2.tauri.app/learn/window-customization/).

The adapter should expose a small outcome to the UI, suppress duplicate pending
requests, and handle rejection without a blank window or unhandled promise.
Never fall back to browser `window.close()` after a failed native close. A neutral
manual-close notice is a safe no-bridge/browser fallback; it must leave Play and
the page usable. Do not claim an absent bridge proves this is a browser, or tell a
native user that their browser refused. Clear notice timers on unmount if timers
remain. Do not force-kill, call process exit, destroy instead of normal close, or
add speculative persistence machinery.

Current active-run persistence is the existing `App.tsx:898` effect through
`writeActiveRun`; this change does not need a save schema or queue. Existing
denied-storage warnings must remain truthful: no new blanket promise that every
session is saved.

Required acceptance, not performed here:

1. Unit adapter cases: public native bridge succeeds, rejects, is absent or
   malformed; repeated activation; return to Play/unmount before delayed notice.
   No native-rejection path calls the browser close function.
2. Fresh synthetic native profile with an engine-valid active run and non-default
   pace/Music/SFX preferences. Launch the exact portable, activate the **Title
   Exit button**, observe that its main window disappears **and the owned game
   process terminates**, then reopen and verify the exact run and preferences.
   Repeat via keyboard activation. OS X/Alt+F4 evidence alone cannot pass this.
3. Ordinary browser tab: Exit yields useful manual-close guidance if closing is
   not available, no broken page and Play still works. No native calls or errors.
4. Actual native denied/unavailable bridge coverage, plus a normal OS-close
   regression check. Native compile and a mocked promise are insufficient.

## 2. Phone fit: reconcile authorities, do not add a second scaling engine

The claim that the current code ignores height entirely is false. `layout.ts`
already classifies compact at `h < 600 || w < 800`; `screens.css`, `book.css`,
`hud.css` and `dialogs.css` all have height rules. The concrete problem is that
some dimensions respond to height while large minima and secondary fit rules do
not respond coherently.

### Gameplay

Keep `PlayShell`'s measured content box and its ResizeObserver as the size input;
it already subtracts actual padding/safe areas. Keep the board a physical square
and the camera's six-tile window unchanged. Do not globally transform/zoom the
DOM, shrink pointer targets, alter camera code or add a per-frame layout reader.

`layout.ts:8` reserves a 440 px compact deck or 352 px emergency deck.
Arithmetic examples below assume the existing compact padding of 4 px per edge
and zero additional safe-area inset; they are **not browser measurements**:

| Viewport | Content box | Square board | Deck |
| --- | --- | --- | --- |
| 844 x 390 | 836 x 382 | 382 | 446 |
| 780 x 312 | 772 x 304 | 304 | 460 |
| 568 x 320 | 560 x 312 | 204 | 352 |

The extreme phone gives the deck most of the width while still struggling with
its contents. Changing only that minimum is insufficient:

- `AdventureHud.tsx:53` independently clamps compact minimap size to 96/128 px
  from global `innerWidth`, even when its measured available height is smaller.
  Replace this split authority with the same reviewed compact fit contract.
- `hud.css:142` requires a 152 px bottom region and absolutely positions the
  bottom-right pad. Header, objective, collections, gaps and map chrome all have
  to fit **above/alongside** it. Reserve that real pad footprint and its >=48 px
  directional sectors before distributing spare pixels.
- `hud.css:154` hides the feedback band in compact layouts. UI-01 requires visible
  feedback there; restoring it consumes real space and must be included in the
  initial proof, not added after a supposed fit pass.
- `.adventure-hud` currently uses `overflow:auto`. Normal-text success means no
  scrolling is needed, not merely hiding the scrollbar or clipping its overflow.
  Preserve the explicit enlarged-text reader separately. Its current heuristic
  also routes objectives longer than 160 characters to reader mode; do not
  relabel an ordinary authored-content fit failure as enlarged-text behavior.
- Compact collection cells are intentionally non-interactive status spans, with
  detail actions in More. Preserve this policy: smaller art must not accidentally
  become tiny, inaccessible buttons.

Smallest fit work: coordinated short-height tokens/output from the existing
layout seam, plus compact HUD CSS and the compact portion of its current fitter.
Leave the primary-landscape calculation and visual tokens unchanged initially.
Use leftover width/height deliberately, not a fixed 0.55 global scale. A smaller
deck remains bounded by the actual minimap/pad widths; do not promise a full-height
board when the width cannot physically accommodate it and required controls.

### Book, Home and dialogs

- Preserve Book's fixed header/tabs and existing `.book-scroll` ownership/return
  state. `book.css:129` already reduces chrome below 500 px, but still reserves
  120 px character art before names/lore, and keeps large page heading/Poggle
  introduction above the cards. Fit the **whole first complete card plus chrome**,
  not just an image or a card reached only after scrolling past every heading.
  Shrink visual padding/art and redundant introductory chrome first; constrain
  card excerpts while keeping complete lore available in the detail dialog.
- The <620 px rule makes tabs 56 px tall/vertical again. Check it with the new
  coordinated short-height rule rather than relying on width branch order.
  `base.css:8` applies `overflow-wrap:anywhere` broadly to controls, explaining
  possible mid-word labels. Scope normal wrapping to the affected compact labels;
  retain emergency wrapping for genuinely long content elsewhere.
- Home already has a short-height composition, but `.title-copy` scrolls and its
  <450 px branch caps it at 83%. Fit its actual actions/progress without that
  normal-text scroller while retaining left actions/right cast and the artwork.
- Sound now contains Music/SFX ranges and PLAY-A pace. Rebase the fit proof on
  **current v0.22.3** content, not v0.22.0 snapshots. Its current three-column
  <450 px rule and 48 px option rows must include all new controls and the real
  close action. Do not change audio values, gesture activation or pace behavior.

## 3. Proof boundary before propagation

First capture 844x390 and 568x320 gameplay and Book against the exact candidate;
add the reported approximately 780x312 visual viewport. Include maximum authored
objective/collections/currencies, not only Maze 1. Freeze matched desktop/iPad
reference states at 1920x1080, 1280x720, 1194x834 and 1024x768 before editing.

Acceptance must inspect actual rectangles and interactions, not just square-board
unit tests. Current `layout.test.ts` proves a width sum and map minima, and even
encodes the 352 px emergency reservation; it does not establish content fit.

- At normal text, board and every required HUD/control are visible, non-overlapping,
  and within the real safe area; neither page nor deck can scroll away. Hint/More
  and the 48 px sectors work at their visible/hit geometry.
- Book header/tabs stay available; at least one complete representative card is
  visible and only its collection body scrolls. Check all five tabs, 0/1/partial/all
  Bestiary, long names, modal return, tab focus and saved scroll.
- Short Home, story/lore, current Sound and maximum-content victory meet the
  existing contract. Long story may use the approved single body scroller with
  fixed action. Never use global clipping as an apparent pass.
- Check 960x540, safe-area extremes, real Samsung browser chrome open/closed,
  resize/rotation, 200% text, Full/Reduced/Static and forced-colour focus. A
  desktop emulation screenshot is not physical phone acceptance.
- Compare primary reference composition side-by-side; no shrinkage of liked
  phone pickup feedback, minimap or art hierarchy as an incidental side effect.
  Leave iPad optical enlargements until phone fit is sound, as the plan requires.
- Re-run accepted pad/input/pace/audio/save and fixed-origin camera geometry
  regressions after PLAY-B rebase. Geometry changes can alter fill cost; report
  exact build/viewport and do not reuse unmatched performance claims.
